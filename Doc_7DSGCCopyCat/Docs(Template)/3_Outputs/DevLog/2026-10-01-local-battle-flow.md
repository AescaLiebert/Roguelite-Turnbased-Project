# Local battle and dungeon flow — 2026-10-01

Owner steering: defer Firebase Authentication for now and prioritize the actual battle-state and dungeon flow on the local guest profile.

## Change

`LocalBattleSession` now resolves opponent turns in its constructor when the opponent has initiative. Previously, the combat presenter correctly disabled player controls on an opponent turn, but the local session only advanced the opponent after a player command. An opponent-first encounter could therefore remain stuck at battle start.

`CoreBattleSceneController` records the last setup event before the local session starts. After the existing formation/CC intro, it plays any opponent opening-turn events generated by the local session, so the visible state transition matches the initiative result.

The existing local route chain remains: profile/loadout → dungeon entry → route choices → frozen encounter → Core battle → run HP settlement → route resume. No Firebase Authentication or online service is required for that path.

## Verification

Built the shared Core and Contracts successfully; both DLLs were written to `Assets/FightingAllstar/Plugins/`, which is the runtime code path Unity loads. Built the host-neutral server application separately as a compile check. All three builds completed with zero warnings and zero errors.

No Unity Play Mode walk-through or automated test was run in this change. The Unity editor was not available in the computer-use app inventory, so the flow has not been visually observed here.

## GDD battle-state follow-up

Compared the current engine with the combat source contract and the battle-screen state table. Implemented the missing local-state pieces that blocked a complete turn loop:

- Opening and turn-start draws now emit `CardDrawn` and `CardsMerged` events. Regular plays merge adjacent duplicates immediately and update the disposable `PlanDraft` preview, including PG gained from merges.
- Accepted actions whose card/actor/target becomes unavailable during earlier actions now emit `ActionFizzled` and consume their queued slot instead of aborting the entire turn. If a planned target is no longer valid, the engine picks the lowest formation-slot living active target and emits the actual target in the play event.
- Turn end is explicit, the completed-owner-turn count advances, and battle ends in a draw at the GDD's 40-turn cap.
- Run encounter fighter IDs now propagate to setup/draw events as well as the fighter/card snapshots, so event playback can resolve actors to the correct scene views.
- The battle HUD now labels round and progress toward the 40-turn limit, and its queue summary distinguishes move commands from plays.

This is a battle-loop slice, not full GDD combat implementation: status/passive timing, reaction queues, all skill families, online deadlines/reconnect, and the complete state-by-state HUD are still outstanding. Build check: `FightingAllstar.Core.csproj` succeeded and emitted both Contracts/Core DLLs into Unity's Plugins folder with 0 warnings and 0 errors. No Play Mode or automated tests were run; the UI script itself still needs Unity compilation and an editor play-through.

## Repository and Battle scene consolidation — 2026-10-02

Removed the obsolete prototype gameplay stack (`GameManager`, `BattleManager`, `TeamDataManager`, `CardDeckManager`, `Unit`, and related test/presentation scripts) from the active Unity project. `CoreBattleSceneController` now owns scene presentation for the Core battle session without referring to or trying to disable the old managers. The retained Battle opening presenter and fighter HUD scripts live together under `Assets/FightingAllstar/Runtime/Presentation/Combat`; the Battle scene no longer contains the duplicate manager components. Old pre-placed fighter views are inactive because the Core scene controller creates the active battle views.

Replaced the adapter's dependency on deleted `TeamDataManager` data with a `FormationSelection` model. The root README now explains that `Shared/FightingAllstar.Core` and `Shared/FightingAllstar.Contracts` are the portable canonical source used by both Unity and the server; Unity loads their compiled DLLs from `Assets/FightingAllstar/Plugins`.
